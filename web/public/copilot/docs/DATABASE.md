# Guest sessions and the database

Many people use the deployed site at once, and none of them should see another's data. Until
sign-in (SSO) arrives, every visitor is a **guest**. The server issues the guest the first time the
browser reaches the API, and the browser keeps it in a cookie.

| What | Whose |
|---|---|
| Copilot conversations and the facts each one established | the guest's |
| Inspection-camera photos (Vision QC, [CAPTURES.md](CAPTURES.md)) | the guest's |
| The live twin the copilot reads (`live_state`) | the guest's |
| Orders and the warehouse rack in the 3D twin | already the browser's own (kept in the browser) |
| The physics kernel's world stream (`/ws`) | shared: one simulated machine, read-only to the public |

## How a guest works

`services/api/guests.py`:

- **Issued by the server, not claimed by the browser.** A random 128-bit id in the cookie
  `stf_guest = <id>.<signature>`. The signature is an HMAC-SHA256 with `STF_SESSION_SECRET`, so an id
  cannot be forged or guessed into someone else's. Whatever `X-STF-User` header a browser sends is
  replaced by the guest's id.
- **A safe cookie.** `HttpOnly` (page scripts cannot read it), `SameSite=Lax` (other sites' requests do
  not carry it), `Secure` over HTTPS, `Path=/`, kept for `STF_GUEST_DAYS` (default 30).
- **No personal data.** A guest record is its id, when it was made, when it was last seen and how many
  visits. No IP address, no browser fingerprint.
- **Lapses on its own.** A guest unseen for `STF_GUEST_DAYS` is removed with its conversations.
- **Forget me.** `DELETE /guest` removes the guest's conversations, photos and live twin at once, and
  clears the cookie. `GET /guest` shows the guest's record and which database is in use.
- **A crawler cannot fill the table.** A client may start 20 guests, then one a minute.

## The database

| Database | When | Notes |
|---|---|---|
| **SQLite** | By default, and in every local run | One file, `STF_DATA_DIR/stf.db` (`STF_DB_PATH` to move it). Nothing to install. On Render's free tier the disk is wiped at each deploy, so guests and their chats last until the next one. |
| **Supabase Postgres** | When `SUPABASE_URL` and `SUPABASE_SERVICE_KEY` are set and the tables below exist | Survives deploys. The same project can keep the photos ([CAPTURES.md](CAPTURES.md)). |

`STF_DB` picks it: `auto` (the default: Supabase when it is ready, else SQLite), `sqlite` or `supabase`.
When Supabase is configured but its tables are missing, the API stays on SQLite and `GET /guest` says
why.

### Local

Nothing to do: `make api` (or the dev server) creates `.data/stf.db` and a session secret in
`.data/session_secret` (both git-ignored).

### Supabase

The schema is a migration in the repo,
[`supabase/migrations/20261017150000_stf_guests_documents_captures.sql`](../supabase/migrations/20261017150000_stf_guests_documents_captures.sql):
the three tables below, the photos' table and their **private** `captures` bucket (JPEG only,
200 kB). Row-level security is on with no policies, and the browser roles (`anon`,
`authenticated`) have no privileges: only the API server, holding the service key, reaches the
data. It is applied to the project *smart tabletop factory* (`buiwsvaowyigqpeprike`, eu-west-1).

To connect the API to it:

1. Supabase dashboard → **Project Settings → API keys** → copy the **service_role** key. It bypasses
   row-level security: it belongs on the server only, never in git, the browser or a chat.
2. Locally, in the git-ignored `.env`:
   `SUPABASE_URL=https://buiwsvaowyigqpeprike.supabase.co` and `SUPABASE_SERVICE_KEY=<the key>`.
3. On Render: `stf-live` → **Environment** → the same two variables (the blueprint declares them).
4. `make db-check`: a round trip through the API's own code with a throwaway guest. It prints which
   database is in use and why (for example "Supabase rejected the service key"), never a key.

The same SQL by hand, for another project, in the Supabase **SQL editor**:

```sql
create table public.guests (
  id        text primary key,
  created   double precision not null,
  last_seen double precision not null,
  visits    integer not null default 1
);
create index guests_last_seen on public.guests (last_seen);

create table public.documents (
  col   text not null,                 -- the collection: "copilot" for the chat's sessions
  owner text not null,                 -- the guest
  id    text not null,
  doc   jsonb not null,
  t     double precision not null,     -- last written
  primary key (col, owner, id)
);
create index documents_owner on public.documents (col, owner, t desc);

-- row-level security on and no policies: only the server's service key reads or writes
alter table public.guests enable row level security;
alter table public.documents enable row level security;
```

### Render

The blueprint (`render.yaml`) sets the guest settings for the `stf-live` service:

| Variable | Value |
|---|---|
| `STF_SESSION_SECRET` | generated by Render: keep it, or every guest starts afresh |
| `STF_DB` | `auto` |
| `STF_GUEST_DAYS` | `30` |
| `SUPABASE_URL`, `SUPABASE_SERVICE_KEY` | set them in the service's **Environment** page to keep guests across deploys |
| `GROQ_API_KEY` (and `GEMINI_API_KEY`) | the copilot's models: set them on the **Environment** page, never in git |

The static `stf-twin` site has no server: everything runs in the visitor's browser, so there is
nothing to share between visitors.

## When sign-in arrives

A signed-in user replaces the guest as the owner. `guests.current()` is the one place the API asks
who the visitor is, and every store keys its documents by that owner. Migrating a guest's data to the
user it signs in as is one update of `owner` in each table.
